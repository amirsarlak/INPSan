# INPSan Official Checkpoint — CP-KB-001

**Title:** Knowledge-Based Product Rebaseline and INPSan 3.3 Engineering Foundation  
**Recorded:** 2026-09-28  
**Status:** APPROVED STRATEGIC CHECKPOINT — implementation begins from a frozen 3.2.x operational baseline

## 1. Decision

INPSan development is rebaselined to optimize simultaneously for:

1. enterprise operational value;
2. proprietary technical depth and demonstrable R&D;
3. knowledge-based evaluation evidence;
4. security-certification readiness;
5. cyber-resilience and passive-defense-oriented operations;
6. long-term maintainability and low key-person dependency;
7. measurable performance and resource efficiency.

This checkpoint does **not** invalidate previously accepted operational work.

## 2. Product boundary

INPSan is **not** a new operating system and is **not** a fork of OmniOS.

### Upstream / foundation
- OmniOS / illumos;
- OpenZFS;
- COMSTAR/STMF;
- operating-system drivers and standard storage services;
- third-party components where explicitly identified.

### INPSan-developed product layer
- monitoring foundation and telemetry contracts;
- historical telemetry and operations data model;
- Dashboard/DataAdapter integration;
- hardware-health and inventory normalization;
- physical disk/chassis reconciliation;
- HPE iLO/Redfish integration;
- live I/O telemetry;
- Event Store and Alert Engine;
- startup-readiness and stability policies;
- notification model and operations UI integration;
- package/verify/rollback engineering.

### Planned proprietary R&D
- independent Control Plane;
- enterprise authentication/RBAC/audit;
- customizable workspace and reporting;
- local predictive intelligence;
- Central Manager / fleet management;
- compliance/cyber-resilience reporting and automation.

Planned R&D must not be represented as implemented product capability until tested and accepted.

## 3. Baseline freeze

The validated INPSan 3.2.x operational line is frozen as the reference baseline.
No broad UI, control-plane, AI or central-management rewrite is authorized directly on the accepted operational line.
Any corrective production work remains narrowly scoped, evidence-based and independently releasable.

## 4. New development line

The next development line is **INPSan 3.3 — Knowledge-Based Productization & Engineering Foundation**.

Initial scope:
- proprietary architecture contract;
- product-specific UX design system;
- source engineering/documentation standard;
- security architecture baseline;
- benchmark/performance harness;
- module/evidence ownership register;
- independent Control Plane foundation;
- testable customization contracts.

## 5. Design principles

### Product-specific UX
UI decisions must originate from documented operator personas, workflows and enterprise-storage operational needs. Design rationale and usability evidence are first-class artifacts.

### Experience-driven operational intelligence
Monitoring, alerts and reports must map to defined operational/security problems and evidence.

### Security by design
Authentication, authorization, audit, secure communications, secrets, secure update and vulnerability management are architectural concerns, not release-end hardening.

### Local-first predictive intelligence
Prediction must rely on locally processed operational telemetry/metadata by default. Observed faults, anomalies, forecasts and recommendations must remain distinguishable.

### Central management safety
Central Manager must not enter the storage data path. Local data service and safe local operations continue during Central Manager outage.

### Evidence before claim
Only implemented, tested and demonstrable capabilities may be claimed as current technology.

## 7. Exit gate for Engineering Foundation

The foundation phase is accepted only when:
- product boundary and ownership are unambiguous;
- each proprietary module has measurable complexity/evidence fields;
- source documentation standard is enforceable;
- baseline performance measurements are reproducible;
- security architecture and TOE boundary draft exist;
- UI design system and personas/workflows are documented;
- Control Plane API/auth/audit architecture is approved before implementation;
- roadmap capabilities remain correctly labeled IMPLEMENTED / PARTIAL / PLANNED.
