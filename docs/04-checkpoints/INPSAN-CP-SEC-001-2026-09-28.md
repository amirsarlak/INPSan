## 1. Decision

INPSan 3.3 security-certification readiness now proceeds through a version-bound evaluation architecture rather than generic hardening alone.

The project will use:
- Common Criteria CC:2022 / CEM:2022 as the evaluation-document structure;
- ISO/IEC 27040:2024 and NIST SP 800-209 as storage-security baselines;
- NIST SP 800-209 Rev.1 Initial Public Draft only as forward-looking guidance;
- OWASP ASVS 5.0 Level 2 plus selected Level 3 controls for high-impact management;
- OWASP WSTG and OWASP API Security for verification;
- NIST SSDF and NIST SP 800-115 for secure development/testing;
- NIST SP 800-63B-4 for authentication guidance.

- INPSan Control Plane;

- security audit;
- secure storage-control workflows;
- secrets/certificates;

This is a draft boundary, not a final certification claim.

## 8. Next implementation sequence

1. Build SFR-to-INPSan traceability matrix from the 146-control security matrix.
2. Freeze Control Plane security-critical interfaces.
3. Implement independent identity/authentication foundation.
4. Implement capability-based RBAC + object/scope authorization.
5. Implement security-audit schema and append-only/protected evidence path.
6. Introduce secure command/storage adapter before state-changing endpoints.
7. Add TLS/session/input validation baseline.
8. Run deterministic negative tests before allowing write APIs.
9. Then proceed to SAN/NAS protocol-policy enforcement and secure update pipeline.

## 9. Safety constraints carried forward

- accepted 3.2.x storage data path remains frozen;
- no production state-changing Control Plane endpoint before security gate passes;
- no notification-channel enablement under this checkpoint;
- no destructive production testing while unrelated high-risk driver RCA constraints remain applicable;
- no secret/private production evidence committed to the public repository;
- PASS requires implementation + test + retained evidence.
